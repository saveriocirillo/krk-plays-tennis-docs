# CLAUDE.md

Conventions for working on the KRKplaysTennis API docs portal. Read this before you change anything.

## What this repo is

A public docs portal for a fictional API, built as Saverio Cirillo's technical writing portfolio. It shows three things: writing quality, a docs-as-code workflow, and docs that work for AI agents as well as humans. Saverio reviews and approves every change. You draft; Saverio decides.

## Ground rules

- **The spec is the source of truth.** `openapi/krkplaystennis.v1.yaml` is written before any page that depends on it. If a page and the spec disagree, fix the spec first (in its own commit), then the page.
- **Never hand-edit the API reference.** It's generated from the spec by `starlight-openapi`. Change the spec instead.
- **Mock limits:** Prism returns the first matching example for a status code. Put the most generic example first, for example `validation-failed` before `invalid-score`.
- **Every code sample must run** against the Prism mock. `scripts/test-samples.mjs` (phase 5) runs every `sh` block that starts with `curl`, every `js` block, and every `python` block in the pages.
- **Fictional data only.** No real people, clubs, venues, or companies. No branding or content from Kong, Sabre, or Ververica.
- **Small scope.** A small, polished portal beats a big, unfinished one. Don't add pages or features outside the current phase.

## Git workflow

- Never commit to `main`. One branch per phase, named `phase-N/short-name`.
- Open a PR with `gh pr create` using the template in `.github/pull_request_template.md`. Don't merge: wait for Saverio's review.
- Keep commits focused, with imperative subject lines.

## API design decisions (v1)

- Base URL: `https://api.krkplaystennis.example/v1` (`.example` is reserved and never resolves). Authorization server: `https://auth.krkplaystennis.example`, with `POST /oauth/token` in the spec so the mock serves it. Its errors use the RFC 6749 format, the only exception to problem details.
- The site publishes the spec at `/portfolio/openapi.yaml` from `src/pages/openapi.yaml.ts`. The quickstart starts Prism from that URL.
- Resources: `players`, `venues`, `competitions`, `matches`. Ratings and match suggestions are sub-resources of players: `/players/{id}/rating`, `/players/{id}/rating-history`, `/players/{id}/match-suggestions`.
- IDs are prefixed strings, such as `plr_`, `ven_`, `cmp_`, and `mat_`. Timestamps are RFC 3339.
- Lists use cursor pagination: `limit` and `cursor` in, `{ data, next_cursor }` out.
- Errors use RFC 9457 problem details (`application/problem+json`).
- Auth: API key for all reads. OAuth 2.0 client credentials with the `matches:write` scope for `POST /matches`, the only write in v1. Organizers submit results. There's no dispute flow.
- `POST /matches` takes an `Idempotency-Key` header.
- Matches have `status` (`completed`, `retired`, `walkover`) and a separate `rating_status` (`pending`, `rated`, `not_rated`).
- Player availability is a list of weekly time windows plus preferred venues. There's no calendar integration.
- `match_format` on a competition is an object of independent rules (`games_per_set`, `no_ad`, `final_set`), never an enum of named formats. Extend it with new optional fields, such as `tiebreak_at` for Fast4 (tiebreak at 3-3), so existing clients don't break.
- Not in v1: doubles, webhooks, player registration, Arazzo workflows, `tiebreak_at`.

## Rating model

Elo with a confidence value. Keep explanations plain and the math reproducible by hand. The spec, the concept page, and every example must use these exact constants.

- **Starting rating** comes from the self-assessed NTRP level (`self_assessed_ntrp`, 1.5 to 5.5 in steps of 0.5): `1000 + (NTRP - 1.5) * 200`. NTRP is only an input scale. Never call the computed rating an NTRP rating.
- **Confidence** is an integer from 0 to 100. It starts at 20, rises by 10 per rated match up to 95, and after 60 days without a rated match drops by 5 every 30 days, down to 20. Inactivity never changes the rating value.
- **K-factor** is 48 when confidence is below 40, 32 from 40 to 69, and 16 from 70.
- **Expected score** = `1 / (1 + 10^((opponent rating - player rating) / 400))`, rounded to 3 decimals.
- **Actual score** is 1 for a win and 0 for a loss. For a retired match, it's the player's share of games won, rounded to 3 decimals. A completed match tiebreak counts as one game.
- **Change** = `K * (actual - expected)`, rounded to the nearest integer. Each player uses their own K, so a match isn't zero-sum.
- Walkovers aren't rated (`rating_status: not_rated`).

## Style rules

These apply to every page, spec description, and README.

- US English, second person, active voice, present tense.
- Sentence case for all headings.
- One task per page. Steps are numbered, and every step states its expected result.
- No marketing language and no filler.
- No em dashes or en dashes as punctuation. Use a period, a comma, a colon, or parentheses.
- No positional references such as "above", "below", or "the following section". Link to the target instead.
- Code samples come in curl, JavaScript, and Python, in that order, inside `<Tabs syncKey="lang">` so the reader's choice persists across pages.
- Samples read the base URL and credentials from environment variables, never hard-coded values: `KRK_API_URL`, `KRK_API_KEY`, `KRK_AUTH_URL`, `KRK_CLIENT_ID`, `KRK_CLIENT_SECRET`, `KRK_ACCESS_TOKEN`. The same sample then runs against the mock, in CI, and in production.
- Each sample is self-contained and runnable as is: JavaScript as an ES module on Node 22 (`fetch`, top-level `await`), Python 3.9 with `requests`. Check `response.ok` or call `raise_for_status()`.
- Fictional people in examples have no stated gender. Refer to them by name, never with "he" or "she".
